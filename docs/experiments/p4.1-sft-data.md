# Phase-4 SFT data (P4.1)

- status: done
- result: this is a data build, not a model experiment. It produced a multi-format training set
  (25,896 examples from 432 train-only worlds, four renderings, Cedar held out), a selection set,
  and one token-matched single-format control per SFT model. Every training policy is disjoint
  from the eval benchmark both by hash and by vocabulary.
- frozen data: `outputs/20261107T214145755710Z_authinv_sft_data/`, built from commit `921120a`
  (clean tree), config sha256 `dd6313355c996025ab433558acbdaca3e4666e4bc192b3b5508c1d1923809cdc`,
  data version `sft-data-v1`. It is checked against the eval benchmark v2 (`0b602a17…`).

## What

The training worlds come from three **train-only domains** (`src/authinv/sft/data.py`). Each
is a world type that appears nowhere in the eval benchmark:
- `ledger`: Clerk / Bureau / Ledger;
- `hangar`: Pilot / Squadron / Aircraft;
- `archive`: Scholar / Faculty / Codex.

They use the P1.6 design grid of 24 cells (single, multi-rule and conditioned tiers; 1–3 roles;
0–3 conditions; with or without a forbid rule). They also keep the P1.6 non-degeneracy rule: at
least 4 allow and 4 deny requests, boundary requests among them, and no dead rule. So the training
policies have the structure of the eval synthetic worlds, but none of their words.

Each world is asked like the benchmark (prompt-v1):
- 2 allow and 2 deny requests, boundary requests first;
- both name assignments (orig and the swap derangement);
- application and interpretation queries.

Every query appears in the **training renderings only**: nl_statement, owner_statement, table
and json_policy, each round-tripped through its exact decoder. **Cedar (`executable`) is held out
entirely**, as RESEARCH_PLAN §3 Phase 4 says, and Rego is unseen too. The target is the exact
object the prompt asks for, and the T2 strict parser scores every target as correct (tested).

The worlds are split by replicate index within every design cell, so each set covers the whole grid:

| set | worlds | examples | renderings | tokens (Qwen3.5-9B) | tokens (Gemma-4-12B) |
|---|---|---|---|---|---|
| `train_multi` | 432 | 25,896 (13,824 application, 12,072 interpretation) | the four training renderings, 6,474 each | 15,608,836 | 15,929,692 |
| `val_multi` (selection only) | 72 | 4,264 | the same four | 2,560,108 | 2,612,022 |
| `control_qwen3_5_9b` | 2,184 | 32,867 | nl_statement only | 15,609,000 (×1.00001) | — |
| `control_gemma4_12b` | 2,189 | 32,953 | nl_statement only | — | 15,930,125 (×1.00003) |

Application labels are balanced in every set (6,912 / 6,912 in `train_multi`).

**The matched-token control.** The plan asks for single-format SFT with a matched token count. It
uses one training rendering (nl_statement, set in the config) and draws from a separate pool of
2,880 worlds. The pool is read in (replicate, domain, cell) order, so any prefix covers the grid
evenly. Drawing stops once the token count reaches `train_multi`'s under that model's own pinned
tokenizer and chat template. The control therefore has more distinct policies, about 5× as many,
in one format; the multi-format set has fewer policies in four formats.

**The no-SFT baseline** is each base model at its pinned revision, with no adapter, on the frozen
benchmark through the Phase-2 T2 harness. That is the Phase-2 T2 run of the model:
`20261014T202735054033Z_authinv_t2_qwen3_5_9b` and `20261014T202748027724Z_authinv_t2_gemma4_12b`.
All six renderings are measured there, Cedar and Rego included.

```sh
uv run --extra inference python scripts/authinv_build_sft.py --config configs/authinv/sft_data.yaml \
  --benchmark outputs/20261008T140619620402Z_authinv_benchmark
```

## Disjointness from the eval benchmark

The build compares its 6,768 training policies (orig and swap) with the benchmark's 3,968, and
refuses on any overlap. Both checks came out empty:

| check | overlap |
|---|---|
| semantic hash (entities, actions, context schema, rules; ids of rules ignored) | 0 |
| entity types, entity ids, actions | 0 / 0 / 0 |
| attribute names, context keys, string values | 0 / 0 / 0 |
| duplicate policies within the training data | 0 |

The vocabulary check bit during development, which shows it isn't vacuous. The first draft of the
domains reused the actions `post`, `annotate` and `restore` and the values `alpha` and `draft`, all
of which occur in CedarBench worlds. They were renamed before the frozen build.

## Engineering note

The first full build matched the controls on example count, not tokens. In transformers 5,
`apply_chat_template(tokenize=True)` returns an encoding dict, so `len()` counted its two keys
(2 "tokens" per example). The builder now reads `input_ids`, and refuses a build that averages
under 50 tokens per example (tested with a broken counter). The bad build was discarded before
anything used it. The multi-format and selection files are byte-identical across the two builds,
because their contents don't depend on the counter.

## Choices left for the Phase-4 preregistration (P4.3)

- **The control's rendering** is nl_statement, a config value. NL is the format real deployments
  use most, and the one with the highest deny→allow rate in Phase 2. json_policy is the obvious
  alternative.
- **Whether Rego counts as a second held-out format** in the report. It never appears in training.
- **Interpretation queries** are in the training data, about 47% of examples, so the model learns
  both tasks of the benchmark. An application-only variant is a config change.

## What a CedarBench "task" contains, and what we import

Each scenario has `policy_spec.md` (prose), `schema.cedarschema`,
`verification_plan.py`, and `references/*.cedar`. The reference files are the
authors' Cedar witnesses for each check (ceilings for `implies` checks, floors
for `floor` checks). CedarBench ships **no single answer policy per task and no
entity data**. So:

- **Unit = one reference file**: a Cedar policy set plus the scenario's
  schema. The verification plan is Python and is never executed.
- **The entity universe is synthesized** deterministically from the schema and
  the policy's own literals. For each principal or resource type, the importer
  builds every combination of the values of the attributes the policy reads
  (Bool: both values; Long: each literal ±1; String: the literals plus
  `__unseen__`; domains are merged across attribute-to-attribute comparisons)
  and every subset of memberships in the literal groups the policy scopes on.
  Caps: at most 64 entities per type and 20,000 requests. Every world's meta
  records `entities_synthesized: true`.
- **Exact rewrites only**: `!x.a` → `x.a == false`, bare boolean `x.a` →
  `x.a == true` (both typed Bool by Cedar's validator), and a missing action
  constraint → all schema actions. Every other construct outside the canonical
  model excludes the file and is counted.

A file **ships** only if all of the following hold:
1. the original text validates against the original schema (Cedar strict validator);
2. it converts;
3. `certify()` passes on every rendering (the five of P1.2 plus Rego from P1.5, with both the Cedar and OPA engine checks);
4. **faithfulness**: the *original* reference text, evaluated by the Cedar engine on the full request universe with the synthesized entities, matches the canonical policy's reference decision on every request, with zero engine errors.

Shipped worlds are deduplicated by semantic hash.

is **mixed** for the benchmark's purposes.

## Caveats and implications for P1.10

- **The shipped set is dominated by templated stress scenarios.** 2,238 of the
  2,547 unique worlds come from five scenarios built to stress the harness
  (e.g. 1,000 near-identical floors). Only 309 unique worlds come from the
  paper's 221 tasks. P1.10 should cap or stratify per scenario rather than
  take CedarBench worlds uniformly.
- **The worlds are small.** A reference file is a single-check witness, mostly
  one `permit` with one condition, and the minimal synthesized universe gives
  about 2 requests. P1.10 needs ≥ 4 requests per world. Making these worlds
  usable means enlarging the universe, for example by adding the schema's other
  actions with the same `appliesTo` as deny probes, or by replicating entities
  per attribute value. Composing a scenario's ceilings into one task-level
  policy is another option. Each of these changes the imported data and needs
  a version bump, so it is left as a proposal for a human decision, not done
  here.
- **Disjunction is the largest single blocker.** 644 files are excluded *only*
  for top-level `||`. An exact DNF split into separate rules (for both permit
  and forbid) would recover them. The step spec counts `||` as an excluded
  construct, so it was not applied. Applying it is a plan decision.
- No entity data exists in CedarBench, so decisions about who is allowed are
  defined over synthesized entities, not real ones.

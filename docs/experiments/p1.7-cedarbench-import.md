## What a CedarBench "task" contains, and what we import

Each scenario has `policy_spec.md` (prose), `schema.cedarschema`,
`verification_plan.py`, and `references/*.cedar`. The reference files are the
authors' Cedar witnesses for each check (ceilings for `implies` checks, floors
for `floor` checks). CedarBench ships **no single answer policy per task and no
entity data**. So:

- **Unit = one reference file**: a Cedar policy set plus the scenario's
  schema. The verification plan is Python and is never executed.
- **The entity universe is synthesized** deterministically from the schema and
  the policy's own literals. For each principal or resource type, the importer
  builds every combination of the values of the attributes the policy reads
  (Bool: both values; Long: each literal ±1; String: the literals plus
  `__unseen__`; domains are merged across attribute-to-attribute comparisons)
  and every subset of memberships in the literal groups the policy scopes on.
  Caps: at most 64 entities per type and 20,000 requests. Every world's meta
  records `entities_synthesized: true`.
- **Exact rewrites only**: `!x.a` → `x.a == false`, bare boolean `x.a` →
  `x.a == true` (both typed Bool by Cedar's validator), and a missing action
  constraint → all schema actions. Every other construct outside the canonical
  model excludes the file and is counted.

A file **ships** only if all of the following hold:
1. the original text validates against the original schema (Cedar strict validator);
2. it converts;
3. `certify()` passes on every rendering (the five of P1.2 plus Rego from P1.5, with both the Cedar and OPA engine checks);
4. **faithfulness**: the *original* reference text, evaluated by the Cedar engine on the full request universe with the synthesized entities, matches the canonical policy's reference decision on every request, with zero engine errors.

Shipped worlds are deduplicated by semantic hash.

## Caveats and implications for P1.10

- **The shipped set is dominated by templated stress scenarios.** 2,238 of the
  2,547 unique worlds come from five scenarios built to stress the harness
  (e.g. 1,000 near-identical floors). Only 309 unique worlds come from the
  paper's 221 tasks. P1.10 should cap or stratify per scenario rather than
  take CedarBench worlds uniformly.
- **The worlds are small.** A reference file is a single-check witness, mostly
  one `permit` with one condition, and the minimal synthesized universe gives
  about 2 requests. P1.10 needs ≥ 4 requests per world. Making these worlds
  usable means enlarging the universe, for example by adding the schema's other
  actions with the same `appliesTo` as deny probes, or by replicating entities
  per attribute value. Composing a scenario's ceilings into one task-level
  policy is another option. Each of these changes the imported data and needs
  a version bump, so it is left as a proposal for a human decision, not done
  here.
- **Disjunction is the largest single blocker.** 644 files are excluded *only*
  for top-level `||`. An exact DNF split into separate rules (for both permit
  and forbid) would recover them. The step spec counts `||` as an excluded
  construct, so it was not applied. Applying it is a plan decision.
- No entity data exists in CedarBench, so decisions about who is allowed are
  defined over synthesized entities, not real ones.

## v2: enlarged universes and an exact `||` split (P1.7.2)

Approved by Jerzy on 2026-10-08 (RESEARCH_PLAN §8: "exact universe enlargement … schema-action probes, extra entities, exact `||` split"). Importer `cedarbench-import-v2` is now the default. v1 can still be selected with `--importer cedarbench-import-v1`. Re-running v1 gives byte-identical `policies.jsonl` (`1aceafaa4fd14692…`) and `equivalence.jsonl` (`79d0947911834836…`), so the v1 sections above remain reproducible history. The CHANGELOG row is `cedarbench-import-v2`.

What v2 changes. It only adds requests and entities, plus one rewrite that preserves meaning:

1. **Action probes.** Every schema action whose `appliesTo` admits the world's principal and resource types, and that declares each context key the policy reads with the same type and as required, joins the world's `actions`. Rules keep the actions they name. Requests for the other actions are probes, and the policy denies them by default. An unconstrained `action` covers exactly these compatible actions, which are the schema-valid ones for the world's types. 2,487 of 2,644 unique worlds gain at least one probe action. Actions per world reach up to 20.
2. **Extra entities.** Each synthesized combination of attribute values and group memberships, built as in v1 (both Bool values, each Long literal ±1, String literals plus `__unseen__`, every membership subset), is instantiated twice (`ENTITY_REPLICAS = 2`). Ids keep v1's `Type_i` pattern and are SAFE. The importer falls back to one copy if a type would exceed 64 entities or the universe would exceed 20,000 requests. No world needed the fallback: all 2,644 have 2 replicas.
3. **Exact `||` split.** A `when` clause whose top-level expression is a disjunction becomes one rule per disjunct. The effect, scopes, and actions stay the same, and ids get the suffix `<id>_or<k>`. The rewrite is exact for permits and, under deny-overrides, for forbids. If there are several `when` clauses, they multiply out, with a cap of 32 rules per reference rule (`disjunction_too_large` otherwise). A `||` below the top level (`A && (B || C)`) is still excluded and counted as `nested_||`.

The shipping rule is unchanged: the source validates, the policy converts, `certify()` passes on all six renderings, and the policy is faithful to the original text. Faithfulness is now checked with cedarpy on the full **enlarged** universe. Each world also records `n_allow`, `n_deny`, boundary counts, `non_degenerate` (P1.6's bar: ≥ 4 allow and ≥ 4 deny, ≥ 2 boundary each), and `dead_rules`. Non-degeneracy does not gate shipping. P1.10 filters on it.

### v2 result

Data audit, **positive** for the benchmark: 382 unique non-degenerate worlds from the paper's 221 tasks, up from 309 worlds of which almost none met the bar. All 2,644 v2 worlds meet the bar. No policy's meaning changed: every world was re-certified and checked against the original Cedar text on the enlarged universe.

### v2 caveats for P1.10

- **The split recovered fewer files than v1's "644 sole-`||`" suggested.** v1 counted only the outermost unsupported construct, so 644 files looked blocked by `||` alone. Once split, the disjuncts of 541 of them contain other unsupported constructs, mostly `in` over an expression and entity comparison (e.g. `owner == principal || principal in resource.editors`), which is why those counts went up. Only 103 files were blocked by top-level `||` alone.
- **The bar is met at its minimum, largely through replication.** The median world has exactly 4 allow requests: one allowed attribute combination × 2 replicas × 2 resource replicas. The replicas are indistinguishable copies with different ids, and many deny requests are action probes. These worlds are non-degenerate by P1.6's definition, but their allow side is narrow. P1.10's request sampling and balancing should keep that in mind (e.g. by also stratifying on the boundary axis).
- **Stress scenarios still dominate**: 2,262 of 2,644 unique worlds. Twenty 25-rule worlds come from splitting the stress scenarios' many-way disjunctions. P1.10 should cap or stratify per scenario.
- Probe actions are restricted to schema-valid requests (`appliesTo` and the context keys the policy reads). An action that declares the key with a different type, or as optional, is not added.
